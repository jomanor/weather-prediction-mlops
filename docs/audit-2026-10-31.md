# Full repo audit — 2026-10-31

Findings from four independent read-only passes (Spark/architecture, UI, correctness/safety/load,
inventory). Nothing was changed while auditing. Line numbers are from `main` at `50ecb0e`; expect
drift after the fixes land.

**Status:** Batch A (findings 1, 2, 6, 12 + S4, S5) and Batch B (3, 4, 5, 11 + S1) are implemented — see the
*Batch A* / *Batch B* sections of `docs/handoff.md` (commits `df39022`, `cfabdf3`, `645ba16`, `04ad956`). Findings below are the state of `main` at `50ecb0e` unless noted.

**Assumed load** (from `docs/handoff.md`, `render.yaml`, the live API): 15 stations (14 Spain +
Pasadena), ~360 raw observations/day, `raw_weather` ≈ 65 k docs at a 180-day TTL,
`weather_features` = 43 880 rows, 75 prediction rows per inference run, 10 models per retrain,
one free Render instance that sleeps after ~15 min, one Atlas M0 (512 MB), GitHub Actions crons
throttled to ~4–7 runs/day.

**Verdict:** the read API and the design system are genuinely good; the *writers*, the threshold
sprawl and the Spark pipeline are where it hurts. Fix 1–7 first, then delete Spark (8) and the UI's
fifth wheel (13–16).

**Score, roughly:** backend read path A−, writers C, pipeline D+ (correct but 10× the machinery its
job needs), frontend architecture A−, frontend information architecture C+ (the database's org
chart), docs C (drifted by 2–3 batches).

## Must fix

### 1. Backfill reports failed writes as "already existed" and exits 0
`scripts/backfill_historical_data.py:338` (`except BulkWriteError`), `:508-513` (`main`)

- **Problem:** any bulk error is assumed to be a duplicate key; `skipped = len(docs) - inserted`,
  then "Backfill complete" and exit 0. Case: Atlas M0 hits quota mid-run → every `WriteError`
  becomes "skipped (already existed) = N", 0 inserted, green run.
- **Fix:** re-raise unless every `details["writeErrors"]` entry is code 11000; make `main` fail when
  `inserted == 0` for a range that was not already covered.
- **Skip cost:** silent data loss that looks like success, on the script you run after an outage.

### 2. Backfill defaults to 4 years — twice the tier — and the TTL deletes it on arrival
`scripts/backfill_historical_data.py:353` (`date(today.year - 4, today.month, today.day)`),
`backend/app/db/mongo.py:42` (`raw_weather` TTL)

- **Problem:** 15 cities × 4 years hourly × ~2 KB ≈ 1 GB into a 512 MB tier, while the TTL deletes
  anything older than 180 days within ~60 s. The default range also crashes on a leap day
  (`date(year-4, 2, 29)` → `ValueError`).
- **Fix:** default `--days 90`; refuse ranges > 180 days; compute the start with
  `today - timedelta(days=365 * 4)` instead of `date(year-4, ...)`.
- **Skip cost:** a backfill that cannot finish, can fill the database, and then feeds finding 1.

### 3. `weather_data` still shadows `raw_weather`: one stale doc hides fourteen stations
`backend/app/repositories/weather_repo.py:248-270` (`latest_for_city`, `latest_per_city`),
`:285-332` (`find_range`, `find_many_in_range`)

- **Problem:** every read tries the legacy collection first and falls back only when it is *empty*.
  `weather_data` has held 0 rows for months, but one manual/legacy document inside its 30-day TTL
  makes `/weather/current` return that single city and `/weather/history/{city}` return one point
  instead of thousands. It also costs one extra Mongo round-trip per hot read.
- **Fix:** read `raw_weather` first and keep `weather_data` as the fallback (the collection and its
  TTL stay in place — hard rule 3).
- **Skip cost:** a confident 200 that is wrong, plus permanent extra latency on the free tier.

### 4. The station list has three sources of truth and the monitors read the wrong one
`backend/app/core/cities.py:20` (`DEFAULT_CITIES`, 15), `backend/app/repositories/city_repo.py:71-91`
(Mongo `cities`, seeded only when empty), `scripts/backfill_historical_data.py:71` (a third dict of
14, no Pasadena), `weather_repo.py:361`, `analytics_repo.py:62`

- **Problem:** ingest follows the Mongo registry; the quality meter, analytics, diurnal and
  correlation surfaces iterate the code constant. Delete a station via `DELETE /cities` and it
  reports `bad` forever; add one and every canonical-city endpoint ignores it. This is the Pasadena
  bug from 2026-10-30, still reachable.
- **Fix:** the constant becomes seed data only; `quality_report` and `CANONICAL_CITIES` read the
  registry (or one shared registry module); drop the backfill's own dict.
- **Skip cost:** station drift between what is ingested and what is monitored, on the next edit.

### 5. "Fresh prediction" has four authorities and three different numbers
`backend/app/core/config.py:58` (24 h), `spark/spark-jobs/inference.py:77-78` (12 h, 0.9 coverage),
`scripts/pipeline_summary.py:54` (0.9), `scripts/watchdog.py:67-72` (12 h / 18 h / 0.90)

- **Problem:** a prediction whose `source_timestamp` is 20 h old is *fresh* in the API, *bad* in the
  watchdog and *warned about* by inference. Tuning one file desynchronises the other three; the
  watchdog docstring itself says "retune the backend first and copy the numbers here".
- **Fix:** one shared thresholds module imported by all four; pick 12 h as the single authority for
  prediction source age (it matches the ~6 h rebuild cadence).
- **Skip cost:** the user-facing badge contradicts the ops alert, which is worse than neither.

### 6. Backfilled hour features are off by one hour across a daylight-saving change
`scripts/backfill_historical_data.py:307`, `spark/spark-jobs/batch_processing.py:202-208`

- **Problem:** one `utc_offset_seconds` (from a single response) is stamped on every hourly doc of a
  multi-month chunk, then used to derive `hour`, `hour_sin`, `hour_cos`. A May→November chunk labels
  winter rows with the summer offset, while live ingest uses the current one: two definitions of the
  same feature in one training set.
- **Fix:** derive the local hour from longitude, or re-request/offset per month.
- **Skip cost:** a quiet accuracy leak no test covers (a retrain is required after the fix).

### 7. `POST /refresh` is an unauthenticated write with per-process quotas
`backend/app/routers/refresh.py:44-54`, `backend/app/core/rate_limit.py`, `core/config.py:65-69`

- **Problem:** gated only by `REFRESH_ENABLED` (default off) plus a limiter held in process memory.
  The free instance sleeps, the counters reset, and each wake buys another 48 writes against
  `raw_weather` — the largest collection in the storage budget.
- **Fix:** require the existing `CITY_WRITES_TOKEN` bearer (same gate as the city writes), or delete
  the endpoint — nothing calls it (see 13).
- **Skip cost:** an open write surface whose cap is an object that gets garbage-collected.

## Should fix

### 8. Spark is doing a laptop-sized job with a distributed framework — drop it
`spark/` (3 140 lines), `.github/workflows/ml-pipeline.yml`

- **What it costs (measured from the repo, not guessed):** features ~62 min, train ~80 min,
  `job=all` ~145 min against a 120-min scheduled cap (the 300-min override is the workaround); the
  Atlas-congestion tail hit **117–119 min** twice; every run installs Java + `pyspark==3.5.5` and
  sets `SPARK_DRIVER_MEMORY=6g`; `mongo_retry.py` (227 lines) exists only because a local-mode Spark
  stage aborts on the first task failure; `spark-scheduler/` + the compose Spark cluster are not
  deployed; MLflow is a third store nobody uses. A 199-line workflow with a stage-resolver job
  exists to schedule three scripts.
- **What it buys:** window functions (`lag`/`lead`/rolling) over ~44 k rows and cross-validated
  training with `parallelism=min(4, cpu_count)`. Both are pandas/polars + scikit-learn
  (`GridSearchCV(n_jobs=-1)`) work, and the data is hard-bounded to single-node size by the M0
  512 MB tier and the 180-day TTL.
- **Migration sketch (~2–4 days):** `batch_processing.py` → pandas/polars feature script (~250
  lines, same `_id` upserts); `ml_training.py` → scikit-learn (~400 lines, keep the same
  `metrics`/`interval`/`diagnostics`/`split`/`data_snapshot` registry fields so `/api/models` is
  unchanged); `inference.py` → pandas + joblib (~180 lines); a ~30-line retry wrapper instead of
  `mongo_retry.py` (pymongo already retries writes). Delete `spark/Dockerfile`, `scheduler.py`,
  `mongo_retry.py`, `setup-java`, the `pyspark` install and the 300-min override. Keep
  `model_selection.py`, `promote_model.py`, `prune_models.py`, `pipeline_summary.py`,
  `watchdog.py`, ingest/backfill.
- **Net:** ≈ **−2 155 lines (−69 %)** of the Spark surface; `job=all` from ~145 min to single digits.
- **Do not migrate:** the data contracts (`raw_weather` shape, `weather_features._id =
  {city}_{epoch}`, prediction `_id = {city}_{epoch}_{h}h`), the TTL/index layout, the
  staging→production→superseded lifecycle, the quality/analytics repositories.
- **Breaks:** existing zipped Spark `PipelineModel`s cannot be loaded by sklearn → one retrain
  (already mandatory under hard rule 1). No collection name, index or API response shape changes.
- **Skip cost:** you keep paying 145 minutes, a JVM and four workarounds for a job that would finish
  before the coffee does.

### 9. The pipeline reads whole collections hourly, and inference queues behind its own long jobs
`spark/spark-jobs/inference.py:229-247`, `spark/spark-jobs/batch_processing.py:101-107`,
`.github/workflows/ml-pipeline.yml:32-34` (`concurrency: group: ml-pipeline`)

- **Problem:** inference reads all of `weather_features` (~65 k rows) every hour just to find the
  newest row per city; the hourly `:05` inference waits behind any in-flight 62–80 min features or
  train run (`cancel-in-progress: false`), so predictions can land ~80 min late on top of GitHub's
  throttling.
- **Fix:** filter `timestamp > now - 48h` server-side in the loaders; give each stage its own
  concurrency group.
- **Skip cost:** the 117-min runs and late predictions stay structural (the current mitigation is a
  retry wrapper).

### 10. The rain label is written twice and the feature list is discovered at runtime
`batch_processing.py:354-355` vs `ml_training.py:273-277`; `ml_training.py:100-160`

- **Problem:** training defines `target_will_rain_{h}h = lead(rain) > 0`, and the persistence
  baseline it is scored against re-derives that rule separately (`rain > 0`, linked only by a
  docstring). Change the threshold in one file and `skill_score` compares the new target with the
  old baseline, silently. Feature columns are chosen by "numeric and ≥50 % present", so renaming a
  feature silently drops it from training while inference keeps scoring the old vector.
- **Fix:** one shared feature/target spec module used by both jobs; a test that
  `data_snapshot.features` equals the spec.
- **Skip cost:** the headline model-quality metric can be wrong with no error anywhere.

### 11. Index creation failure is swallowed and the two heaviest reads have no cache
`backend/app/main.py:61-65`, `backend/app/routers/predictions.py:341`,
`backend/app/routers/weather.py:197-245`

- **Problem:** `ensure_indexes` failure is logged and ignored, so the API serves forever without
  indexes and every read becomes a collection scan on a single free-tier worker. `/predictions/latest`
  and `/weather/series` run full aggregates per request while `/cities` and `/quality` are cached.
  Registry writes never invalidate `cities:list` (60 s of staleness after an add).
- **Fix:** surface the index failure in `/health/ready` or `/metrics`; wrap the two reads in the
  existing `cached(..., 30)`; invalidate the cities key on write.
- **Skip cost:** your slowest endpoints are the uncached ones, on the tier where latency hurts most.

### 12. The tests that should catch the data bugs assert source text instead of behaviour
`tests/unit/test_backfill.py:44-60`, `tests/unit/test_watchdog.py` (env-derived defaults — fixed
2026-10-31), `upsert_batch`/`BulkWriteError` untested

- **Problem:** a test greps the script file for `$setOnInsert`, so it passes whether or not the code
  works; the error branch that finding 1 lives in has zero coverage. The watchdog suite passed
  locally only because no `GITHUB_*` variable was set and went red on Actions for a day.
- **Fix:** call `upsert_batch` with a fake collection that raises `BulkWriteError`; assert duplicates
  skip and real errors raise. Audit remaining tests for ambient-environment dependence.
- **Skip cost:** the next data-loss bug ships green too.
